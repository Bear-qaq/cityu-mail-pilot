# 首页截止日历（2026-10-12）

用户原话：

> 可以直接在软件首页看见这个类似日历上带有分析完邮件后自动上载到这个日历界面，
> 做到一个自动的效果。检测到邮件 → AI 分析 → 提取到有日期 ddl 等 →
> 导入软件自带日历 → 显示

## 先说那条不存在的步骤

「导入软件自带日历」这一步**没有实现，因为它不该存在**。

截止时间在 worker 分析邮件的时候就已经抽出来存进报告了（`reports.deadline_of`），
日历是在**读取时**按截止日把同一批任务分格。所以：

```text
收到来信 → worker 调模型出报告 → 报告里有 action 和截止时间 → 首页日历按截止日分格
```

第三根箭头之后没有任何动作。反过来说，如果真做一张「日历表」再往里写一遍，
就会有第二份副本，而它和报告只会在某一次改动之后才开始不一致 —— 那种不一致
没有任何人能从界面上看出来。整块日历因此是一个**视图**，不是一块存储：

> 一条任务只存在于一个地方（报告正文），首页日历、清单和导出文件都只是它
> 不同的看法。

## 它长什么样

首页「今天要处理的事」**下面**一张卡，默认展开：

- 月历网格，周一开头，固定七列；
- 有截止事的日子一个蓝点（未处理）／灰点（已处理），点开在下面列明细；
- 明细每条带一颗「✓」可以直接标为「处理好了」；
- 左上角 ‹ › 翻月，翻走之后出现「回到本月」。

放在清单下面而不是上面：那一块是今天要动手的，日历是「什么时候到期」的全景。
把动手的事挤到第二屏是拿主次换好看。

## 六条决定，以及理由

### 1. 按**截止日**排，不按来信日

这是这块卡唯一重要的语义决定。app 其他地方（每日清单、每日简报、按天回看）
都按**来信那天**分桶，因为那些地方回答的是「今天有什么要我处理」。

日历回答的是「什么时候到期」，所以它按截止日排，用的是**和 `.ics` 导出同一个**
`taskexport.deadline_day_and_clock`。两处对同一条任务必须说同一天 —— 否则
用户会看到「app 说周四、手机日历说周五」，而这种事他根本
没办法描述清楚。有一条测试专门把日历格子里的日子和导出文件里的 `DTSTART`
对起来验（`test_the_calendar_and_the_download_export_name_the_same_day`）。

### 2. 没有可解析截止时间的任务，落在来信那天，并且**说出来**

兜底是实话，但不能当成「信里写的日子」。payload 里每一条带 `dated` 字段，
界面据此显示「截止 2026-10-15 23:59」还是「邮件里没写截止时间，这是来信那天」。

这与 v1.5.1 修过的那个 bug 是同一条铁律（`docs/task-export-2026-09-16.md` §2.1：
「截止 Oct 8 05:00」被当成来信日 05:00 的那次）：**猜出来的日子不许长得像
信里写的日子**。

### 3. 「稍后提醒」的任务**留在**日历上

稍后提醒的意思是「别再在待办清单里烦我」，不是「这件事不在这天到期」。日历是
放截止时间的地方，把真实的截止时间从这里藏起来，就是让唯一回答「什么时候到期」
的那块地方说谎 —— 而那个矛盾，用户只会在错过之后才发现。

### 4. 往回看多远，是**报告**的回看窗口，不是日历的

任务是从报告重建的，而报告只能按它那封邮件**到达的本地日**去取，所以
`/api/tasks/calendar` 一次查的是
`[这个月 1 号 − INFE_PILOT_CALENDAR_LOOKBACK_DAYS, 这个月最后一天)`。

默认 60 天（`INFE_PILOT_CALENDAR_LOOKBACK_DAYS`）。后果要写下来：**9 月来信、
10 月截止**的任务在 10 月看得见（这正是这个功能存在的形状），但**来信比这个窗口
还早**的任务不会出现在任何月份的格子里。这是「重建」这个设计必然的代价，不是
缺陷；要更宽就调那个环境变量。

### 5. 急事标红：圆点 + 边框（2026-10-16，用户建议）

> 原话：请你在日期下方的圆点，可不可以在事件较为紧急的时候变成红色的。
>
> 后来：可以让 ddl 较为紧急的那一天**日期的边框**也变成红色，从而达到更加醒目的
> 效果吗。

**「急」不是日历自己发明的判据。** `urgent` 由服务端给，取的是
`reports.PRIORITY_HIGH` 判定的结果，而值本身是 `effective_priority` —— 也就是
**用户自己设的轻重缓急压过报告之后**的那个。所以用户在清单里把一条降成「缓」，
那天的圆点会跟着变回蓝色（有测试钉住这一条）；已经处理掉的急事也不再标红，
因为红点是「还要你做什么」的信号。

**红色用的是 app 自己的那个红。** `reports._PRIORITY_COLORS[高][0]` 就是
`#b42318`，也就是 CSS 里的 `--bad`。同一天在清单里标红、在日历上标红，用户才会
认为它们是同一件事；日历另挑一个红，只会多出一种"这个红是哪个红"的疑问。

**红的是两层：圆点，以及这一格的边框。** 圆点只够说明「这天有急事」，一个月里
扫一眼找不出来；边框把整格圈起来才扫得到。边框还比普通格子的绿边**粗一档**
（2px 对 1px）—— 这一条不只是好看：纯靠颜色等于把这条信息从色觉障碍的人眼前
拿走，粗细是一个不依赖颜色的第二信号。`box-sizing:border-box` 是全局的，所以
加粗不改格子外框尺寸，整片网格不会跟着抖。

**圆点的尺寸一个字没动。** 圆点一大，格子里的内容就会跟着上下跳，而
`aspect-ratio` 那套尺寸约束就是为这件事定的 —— 边框加粗是安全的（外框不变），
圆点变大不是。

**选中的那一天改用「更厚」表达，不跟红抢颜色。** 这是量出来的一个坑：自动选中
当天之后，`current` 那圈描边和急事的红框叠在同一格上，实测 10 月 16 日
（今天、已选中、含急事）在屏幕上是「2px 红边 + 2px 绿描边」，看上去根本不像红的
—— 而那恰恰是用户最需要看清的一天。现在颜色只表示急不急，**厚度**表示是不是
正打开着它：选中的急事日是更厚的一圈红。

**无障碍标签也说了。** `aria-label` 形如「10月16日 周五，3 件待办（含急事）」，
读屏能读出来。

### 6. 午夜归前一天（2026-10-16，用户指出）

> 原话：有些 ddl 会设定在 0 点。10.16 号晚上 12 点的 ddl 是我在 16 号睡前就应该
> 做完的，而不是归到 10.17 的 0 点，我认为这里需要有辨析的能力。

**那一刻是 16 号的第 24 点，不是 17 号的第 0 点。** 邮件里写的
``截止：2026-10-17 00:00`` 会被解析成 ``2026/10/16 24:00``，于是它落在 16 号那一格。

**修在 `reports.deadline_of`，不是修在日历里。** 那是全项目**唯一**生成截止时间
字符串的地方，所以清单、日报、清单归档、`.ics` 导出和首页日历会**一起**对上；
只修日历的话，格子在 16 号而旁边那行字还写着 17 号，等于换一种方式自相矛盾
（这一整块的设计前提就是「同一条任务只存在于一个地方」）。

三个附带效果是刻意的：

1. **写成 24:00 就不会长出假约会。** `taskexport` 认时刻的那条正则不收 24 点，
   所以这种任务自然落成一个**全天**事件，而不是一个凌晨 0:00–1:00 的约会。
2. **只有正好 00:00 走这条规则。** 00:30 之后是明确的凌晨，不再有歧义；`23:59`
   这类写法一个字都不动（「截止时刻是邮件说的，不是我们猜的」，见
   `docs/task-export-2026-09-16.md`）。
3. **跨月、跨年都退到真实存在的那一天**：`11月1日 00:00` → `10月31日 24:00`，
   `2027/1/1 00:00` → `2026/12/31 24:00`；原本没写年份的写法退回前一天也不会
   凭空长出一个年份。

配套还得改一处容易漏的地方：`taskexport._already_states` 判断「动作里是不是已经
写过这个截止」，原文写的是 `17 日 00:00` 而我们的标签是 `16 日 24:00` —— 不认
这一对，同一行就会印出**两个**截止时间。所以那里多了一条「同一个瞬间的另一种
写法」的比对。

## 服务端

`GET /api/tasks/calendar?month=YYYY-MM`（需要登录，只读）：

```json
{
  "month": "2026-10", "label": "2026 年 10 月", "today": "2026-10-12",
  "days_in_month": 31, "first_weekday": 3,
  "prev": "2026-09", "next": "2026-11",
  "cells": [{"day": "2026-10-15", "open": 1, "done": 0,
             "items": [{"task_key": "…", "text": "…", "deadline": "2026/10/15 23:59",
                        "clock": "23:59", "dated": true, "priority": "high",
                        "subject": "…", "task_day": "2026-10-12"}]}],
  "counts": {"open": 6, "done": 0}, "lookback_days": 60
}
```

- `first_weekday` 和 `days_in_month` 由服务端给，**浏览器不自己算日历**：每个
  地区对「第一列是周日还是周一」的看法都不同，那种规则写在两边迟早有一边是错的。
  `0` = 周一。
- `month` 非法（`2026-13`、`2026-1`、旧书签里的 `2026-10-05`）一律**回退到本月**，
  不报错 —— 和 `_local_window` 处理 `day` 是同一条规则：只读页面不能被一个
  拼错的查询串变成 500。
- 任务推导抽成了 `_tasks_over_window`：日历和「今天要处理的事」读同一批报告、
  套同一份用户决定，所以两处只可能对**窗口覆盖哪些任务**有分歧，不会对
  「一条任务是什么」有分歧。

## 已知限制

- **手机系统不会提醒你。** 这是网页里做的日历，没有推送、没有锁屏通知。要真正的
  手机闹钟只剩原生 App 一条路，而项目已经决定不做（见 README「已知限制」）。
  这一块解决的是「打开 app 一眼看到什么时候到期」，不是「到点响」。
- **没有真机验证过。** 用无头 Edge 在 390×900 下量过：网格 34 格（10 月
  31 天 + 3 个空格）、今天自动选中、翻月正常、无横向溢出（`scrollWidth -
  innerWidth = 0`）、无 JS 异常。iOS Safari 上的实际手感没有验过。
- 明细里只有**待处理**的条目，已处理的只给一个数量。要看处理过的，
  回上面的清单点开「已处理」。
- **演示页（`/demo`）上没有这块日历。** 演示数据是一份冻结的 fixture，
  里面没有 `/api/tasks/calendar` 的数据，所以那一块在演示模式下整块隐藏 ——
  与其让访问者看到「演示里没有这个接口的数据」，不如不显示。要让演示也有它，
  得把这一格的推导接进 `pilot_app/demo.py` 的 fixture 生成里。

## 稳定性：五个真会坏的地方（2026-10-16 复查后修）

这一轮不是在「优化」，是把**能坏的边界**逐个找出来。每一条都配了测试。

### 1. 极端年份会 500（真 bug，已修）

`?month=9999-12` 找月末要算 `dt.date(10000, 1, 1)`，`?month=0001-01` 的回看窗口
要退到公元 0 年 —— 两个都在 `datetime` 里真的抛。也就是说**一个查询串就能把只读
页面打成 500**，而这正是 `_local_window` 一开始就防的那类事。

修法：`_calendar_month` 只接受 **1970–2100**，其余（含这两个）一律退回本月。
`CALENDAR_MIN_YEAR` / `CALENDAR_MAX_YEAR` 是唯一的出处，注释里写了为什么
不能只校验「能不能解析成一个日期」。

### 2. 一行读不出来的报告会让整个首页 500（真 bug，已修）

`decrypt` 失败会抛 `SecurityError`。以前只有「今天」那几封会被解密，坏一行最多
毁掉一天；日历把窗口放宽到 60 天之后，**每一封旧邮件都进了首页加载的路径**。
真实的触发方式不是攻击，是运维：拿着另一个主密钥恢复一份数据库，全库都读不出来。

修法：`_tasks_over_window` 逐行解，读不出来的跳过并计数，并且把数量放进 payload
的 `unreadable`，界面上明写「另有 N 封邮件的报告读不出来」。跳过是必须的，
但**跳过和丢信在用户眼里长得一样**，所以这件事不能只留在日志里。

（`task_day_view` 仍然不跳过 —— 那只影响已经被打开的那一天，改动它属于另一件事。）

### 3. 翻月按钮：两个都会咬人的毛病（真 bug，已修）

**乱序渲染。** 点两下 `‹` 会发两次请求，回来的顺序没有保证；谁最后到就用谁，会把
用户已经翻过去的月份又画回来，看起来像「点了没反应」。修法：一个自增序号，
**只有最后一次发起的请求允许写界面**。

**连点被吞掉。** 只做上面那一条还不够：三下 `‹` 如果每次都从「服务端上次回的
`prev`」去算目标月份，三次读到的都是同一个值，于是三次都在请求同一个月 ——
用户点了三下，只退一个月（在真浏览器里量到的就是「三下退到 9 月」）。

修法：目标月份由 `calendarWanted`（上一次**想去**的月份）接着算，每一下都算数；
服务端实际回的月份再校准它（翻过 1970-01 时服务端会退回本月，不校准的话后面
每一次点击都会按一个服务端根本不肯给的月份往前算）。

配套把 payload 里的 `prev` / `next` 删掉了：它们的唯一消费者就是那三颗按钮，
留着就是一段没人用的接口。网格形状（第一个是周几、这个月几天）仍然由服务端给 ——
那一条才是会因地区而异的规则，而「上一个月是哪个月」与地区无关。

### 4. 长链接会把页面撑出横向滚动（已修）

模型给出的行动里可能带一条没有空格的长 URL。`min-width:0` 只解决 flex 不肯收缩，
不肯断行的长串照样撑破 360px 宽度。`.cal-item .body > div` 加
`overflow-wrap:anywhere`（app 别处的 `.tasklist` 为同一个原因写过 `word-break`）。

### 5. 三颗按钮里缺一颗，会让后面所有接线一起不跑（已修）

顶层 `$('cal-prev').addEventListener(...)` 拿不到节点就抛，而抛出点**在**
`pause` / `logout` / `export-data` / `delete` 这些接线之前 —— 症状是一个和日历
毫不相干的故障。三颗都改成逐个判空。

### 没有做的事：缓存，以及为什么

实测（`bench_calendar.py`，300 封报告 / 91 天窗口，取 5 次里最快的一次）：

| | |
|---|---|
| 整月推导 | **156 ms** |
| 其中 SQL 查询 | 4.9 ms |
| 其中解密 | 2.4 ms |
| 其中 `parse_report` | **106.7 ms** |
| 一次「输入指纹」查询（缓存可以用来失效的键） | 2.6 ms |

结论是**不加缓存**。理由：

1. 156 ms 是**每次首页加载**的代价，而那台机器是线程化的 Web 服务 —— 一个请求
   慢 156 ms 不会挡住别人。按本项目 220 个账号的上限算，一天总 CPU 增量在
   几百秒量级，不是瓶颈；
2. 唯一能保证不陈旧的失效键是「输入指纹」（`reports` 与 `task_states` 的
   count + max），因为 worker 是**另一个进程**在写新报告 —— 进程内缓存在它
   写完之后收不到任何通知；
3. 一个失效键写漏一处（比如以后新增一个改任务状态的接口），症状是「办完了却
   还在」，而这个项目里最不能接受的就是这种**看起来什么都没发生**的丢失。
   省下 153 ms 换一个静默不同步的失效模式，不划算。

门槛写在这里：等某个用户的报告数到 **1000 封以上**（约半秒），或者这台机器上
同时在线的人明显变多，再回来按第 2 条做缓存。

## 测试

`test_task_calendar.py` 16 条：网格几何、空月份、非法月份回退、**极端年份回退**、
**区间内每个月份都能画出来**、截止日 vs 来信日、
无法解析的截止时间、跨月不串台、**与 .ics 导出的日子一致**、已处理计数与不再列出、
稍后提醒仍在日历上、跨账号隔离、**读不出来的报告不拖垮整页且如实报数**、
没有要跳过的也不能少那个字段、payload 字段。
